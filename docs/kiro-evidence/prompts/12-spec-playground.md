Write a fourth spec, `playground`, in .kiro/specs/playground/ (requirements.md, design.md, tasks.md), following .kiro/steering/kiro-workflow.md. Read docs/product-brief.md, all steering, the three existing specs and the code in skeleton/ (engine, shell, build) first. Write nothing outside .kiro/specs/playground/.

Why: the checker is the heart of the project, but today it is only visible in a terminal. A judge should be able to delete one rule from the licence table and watch a gap appear and the app refuse to build, then undo it, in the browser, in ten seconds.

What to build: a page at `dist/playground/` (linked from the landing page as the first thing after the two app cards: "Break a table and watch the checker catch it").
1. Left: a table editor. A plain `<textarea>` with the table JSON (monospace, line numbers not required), and buttons to load three examples: Which licence? (default, because it is small: 7 rules), Which bin?, and the broken demo table. A "Reset" button restores the loaded example. Optional but wanted: a short list of the rules with a "remove" button per rule, so the judge can break the table without editing JSON; removing a rule edits the JSON text.
2. Right, updated as you type (debounced, about 250 ms): a status line ("Passes: 7 rules, 32 combinations, all covered" or "Fails: 4 gaps, 0 conflicts"), the count of combinations covered out of the total, the structural errors with their paths (including invalid JSON with a line and column), the gaps with up to 5 example combinations, the conflicts with the two rules, their outcomes and an example. All from the same engine (`validate`, `check`), bundled for the browser.
3. Under it, the generated app itself, running from the table being edited, through the real shell, when the table passes; when it does not, the app area says it would not build and why (the same rule as `npm run build`). The preview uses the copy and theme of the example that was loaded (the playground ships the copy and theme of both apps; for the broken demo, Which bin?'s). The theme's custom properties apply only inside the preview.
4. This needs the shell to be mountable: refactor skeleton/shell so the app can be mounted into a given element with a given table and copy (for example `mountApp(root, table, copy, options)`), used both by the normal app pages and by the playground. The normal pages must behave exactly as now (every existing e2e test stays green unchanged). In the preview, the URL hash must not be touched (an option), so the playground page's own state is not mixed with the app's.
5. Accessibility: labelled textarea, the status region is a polite live region (announce only the summary line, not every keystroke), buttons are buttons, focus visible, works at 390 px wide (editor above, results below), axe clean light and dark. No innerHTML with user text: the table JSON is untrusted and must only ever reach the DOM as text nodes.
6. Static only: no server, no network, no storage. All words on the playground come from a playground copy file (skeleton/playground/playground.json or similar).
7. Structure: put it in skeleton/playground/. It may import the engine and the shell; record this as a Departure for the owner to add to structure.md (the owner edits steering, not you).

Tests, proportionate: a few vitest unit tests for the playground's pure logic (parse + check summary, rule removal editing the JSON, error position for invalid JSON) and one property if there is a real universal claim (for example: removing any one rule from a passing table either keeps it passing or yields a gap whose example matches no remaining rule). Two Playwright tests: (a) load Which licence?, remove one rule, see "Fails" with a gap example and the app replaced by the "would not build" notice, press Reset, see "Passes" and a working app; (b) type invalid JSON, see the error with a position. Axe on the playground in light and dark. The build test covers the new dist/playground/ output.

Tasks: at most 6, each with one Verify command. End with a summary: criteria, properties, tasks, and open questions.
