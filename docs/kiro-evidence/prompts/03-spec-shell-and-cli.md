Scope:
1. **copy.json format**, defined here and validated at build time (a hand-written check in skeleton/build, no zod): `title`, `tagline`, `intro`, `answerStyle` (`tiles` or `list`), `labels` (start over, change, why, rule, what mattered, source, read on, not asked, copy link, link copied, show the whole table, hide the table, any, question n of at most m, bad link answers ignored), `resultLead` (e.g. "Put it in"), `footer` as a list of `{ text, href? }`. Every visible word on the page comes from copy.json or the table.
2. **theme.css contract**: only custom properties on `:root` and inside `@media (prefers-color-scheme: dark)`: colours (bg, surface, text, muted, accent, accent-text, border, focus), font stacks for body and headings, radius, a spacing unit. The build rejects a theme.css that contains a selector other than `:root` (one regex check). The shell's own CSS uses only these properties.
3. **The page shell** (skeleton/shell/): `shell.ts` bundled by esbuild into `app.js`, `shell.css`, an HTML template. The build inlines the table and copy as `<script type="application/json">` blocks, so the page makes no requests beyond its own files. Behaviour as in the brief: one question at a time with real buttons, answers so far with "change", result with outcome, detail, note, why (rule ids, what mattered as "question: answer", source title linked, published and read dates), skipped questions, share link in the URL hash with a copy button (the hash is updated with `history.replaceState`; opening a link applies valid answers and shows a notice if any were ignored), the whole-table view as a real `<table>` with `<th scope>` headers. Focus moves to the new question heading or the result heading (tabindex -1). One `h1`. A live region announces the new question. Tiles grid at least 44 px targets; works at 360 px with no horizontal scroll; `prefers-reduced-motion` respected. No inline event handlers, no `innerHTML` with table or copy text (text nodes only), so a table cannot inject markup.
4. **Landing page**: `dist/index.html` lists every app (title, tagline, link) using a small fixed copy in skeleton/shell/landing.json and a neutral built-in theme.
5. **Build** (skeleton/build/build.ts, `npm run build`): for each folder in apps/: validate and check the table (any error, gap or conflict stops the build with the CLI's message and exit 1), validate copy.json and theme.css, write dist/<app>/index.html, app.js, shell.css, theme.css. Then the landing page. Relative links only. Never builds skeleton/examples/ or skeleton/template/.
6. **CLI** (skeleton/cli/bones.ts, `npm run bones -- ...`): `check <table.json>` and `new <name>` as in the brief; output format for check: one line per structural error (`path: message`), then `gaps: N` with the examples as `condition=value, ...`, then each conflict as `conflict: rule-a -> outcome-x vs rule-b -> outcome-y, e.g. condition=value, ...`, then warnings, then `ok: C conditions, K combinations, R rules` or `failed`. Exit codes 0, 1, 2.
7. **Template** (skeleton/template/): a tiny valid app (2 conditions, 3 outcomes, 4 rules) with copy.json and theme.css; `new` copies it to apps/<name>/ and sets the table id and copy title from the name. Name must match the id pattern; refuse an existing folder.
8. **Examples** (skeleton/examples/): `gap.table.json` (one gap), `conflict.table.json` (one conflict). The apps spec adds a broken copy of which-bin later.
9. **MCP server** (skeleton/mcp/server.ts, stdio, dev only, `npm run mcp`): tools `check_table` (input: `path` to a JSON file inside the repo, or `table` inline; output: validate errors or the check result, as JSON text) and `evaluate` (input: `path`, `answers` object; output: the decide result). Paths outside the repo root are refused. zod for tool input schemas only.

Tests, proportionate: a few build tests (builds a temp copy of the template; rejects a table with a gap; rejects a theme.css with a selector), CLI tests (check exit codes on the two examples and the template; new into a temp apps dir, then the built output exists; refuses an existing name), one MCP test that starts the server over stdio with the SDK client and calls both tools. No browser tests here: e2e with axe belongs to the `apps` spec. Correctness properties only where there is a real universal claim (for example: for all valid tables, copy and answers, the hash written by the shell decodes back to the same answers; for all table text, the built page contains it only as escaped JSON). Keep it to at most 3 properties, numbered from 11.

Tasks: at most 8, each with one Verify command. End with a summary: criteria, properties, tasks, and open questions.
